# 漏えい等対応マニュアル(たたき台)

2026-09-20 · @Someone
対象サービス: kyurl.link
関連文書: 利用規約第9条、プライバシーポリシー第6条・第7条、アーキテクチャドキュメント第7.1節・第14節

## 0. このマニュアルの位置づけ

個人情報保護法上の「漏えい等報告」「本人通知」の義務は、事業規模・営利/非営利を問わず、個人情報取扱事業者であれば発生する。kyurl.linkは会員登録(メールアドレス・パスワード)を扱うため対象となる。1人開発のため大がかりな体制は組めないが、**期限だけは絶対に守れる最低限の手順**を事前に固定しておくことを目的とする。

平時にやること:
- 本マニュアルを`docs/`配下に保管し、年1回程度見直す
- 個人情報保護委員会の漏えい等報告フォームのURLをブックマークしておく
- 本人通知用のメールテンプレートを事前に用意しておく(第5節)

## 1. 該当性判定(4類型チェックリスト)

漏えい(またはそのおそれ)に気づいたら、まず以下のどれかに当てはまるか判定する。**1つでも該当すれば報告・通知義務が発生する**(件数の多寡は類型1〜3では問わない)。

| # | 類型 | kyurl.linkでの具体例 | 該当 |
|---|---|---|---|
| 1 | 要配慮個人情報(病歴・犯罪歴等)の漏えい等 | kyurl.linkはそもそも取得していないため通常は非該当 | ☐ |
| 2 | 不正利用により財産的被害が生じるおそれがある個人データの漏えい等 | ログインID・パスワードの組み合わせが漏れた場合(送金・決済機能がなくても、ID・パスワードの組合せ漏えいは典型例として挙げられている点に注意) | ☐ |
| 3 | 不正の目的をもって行われたおそれがある行為による漏えい等 | 不正アクセスによるD1・R2からのデータ窃取、内部(自分自身のミスではなく第三者)による持ち出し | ☐ |
| 4 | 本人の数が1,000人を超える漏えい等 | 設定ミスでR2バケットやD1エクスポートがインターネット上に公開状態になり、1,000人超のユーザーデータが閲覧可能だった場合 | ☐ |

判定に迷う場合は「疑わしきは該当」で動く。**確証がなくても「発生したおそれ」の段階で義務は生じる**ため、調査を待ってから動き出すのは厳禁。

## 2. 初動対応(0〜2時間を目安)

1. **被害拡大の遮断を最優先**
   - 不正アクセスが疑われる場合: 該当するBetter Authのセッション・APIキーを即座に無効化
   - 設定ミスによる公開状態の場合: R2バケットの公開設定・D1へのアクセス経路を即座に閉じる
   - 特定の`links`/`qrcodes`が悪用されている場合: 該当レコードを`status: suspended`に変更
2. **時刻・気づいた経緯を記録開始**(この記録が後の速報・確報の起点になる)
3. **第1節のチェックリストで該当性を仮判定**(暫定でよい)

## 3. 個人情報保護委員会への報告

該当性ありと判断したら、以下の2段階で報告する。

| 区分 | 期限 | 内容 |
|---|---|---|
| 速報 | 事態を知ってから**概ね3〜5日以内**(法令上は「速やかに」) | その時点で把握している範囲でよい。全部揃うのを待たない |
| 確報 | 事態を知った日から**30日以内**(類型3=不正の目的による場合は**60日以内**) | 概要/漏えい情報の項目/本人の数/原因/二次被害の有無/本人への対応状況/公表状況/再発防止策 等9項目。合理的努力を尽くしても不明な事項は判明次第追完してよい |

- 提出先: 個人情報保護委員会「漏えい等報告フォーム」(Webフォーム)
- 起算点: 自分が事態に気づいた時点(その日を1日目とする)
- 速報の時点で全項目が判明していれば、1回の報告で速報・確報を兼ねてよい

**速報テンプレート(下書き)**

```
1. 概要: [いつ、何が、どのように発生したか(判明分)]
2. 漏えいした個人データの項目: [メールアドレス/パスワードハッシュ/短縮URL・QRデータ 等]
3. 本人の数: [件数、または「調査中」]
4. 原因: [不正アクセス/設定ミス/その他、判明分]
5. 二次被害の有無: [判明分]
6. 本人への対応状況: [第5節参照]
7. 公表の実施状況: [公表する/しない、判明分]
8. 再発防止策: [判明分]
9. その他参考事項:
```

## 4. 委託先経由の漏えいの場合

kyurl.linkはCloudflare(D1/R2/Workers等)上で稼働しているため、Cloudflare側に起因する事故の場合も、**報告義務を負うのは委託元であるkyurl.link運営者側**が原則(委託先が把握事項をすみやかに委託元へ通知した場合は委託先の報告義務が免除される仕組み)。「インフラ側の問題だから自分は関係ない」とはならない点に注意。

## 5. 本人への通知

- 法的根拠は委員会への報告とは別に発生する義務
- 時期: 「事態の状況に応じて速やかに」(委員会への確報の30日/60日まで待てるものではない)
- 通知事項: 概要/漏えいした情報の項目/原因/二次被害の有無・内容/本人が取れる防御策、の5項目(9項目全部ではない)
- 方法: 登録メールアドレス宛にCloudflare Email Service(`no-reply@kyurl.link`)経由で送信
- 通知が困難な場合(メールアドレスが不通等)は、サービス上での公表+問い合わせ窓口(`info@kyurl.link`)の掲示で代替可

**本人通知テンプレート(下書き)**

```
件名: 【重要】個人情報漏えいに関するお知らせとお願い

[氏名/アカウント]様

日頃よりkyurl.linkをご利用いただきありがとうございます。
[発生日]、当サービスにおいて下記の事案が発生したことが判明しましたのでご報告いたします。

■ 概要
[判明している範囲で]

■ 漏えいした可能性のある情報
[メールアドレス/パスワードハッシュ 等]

■ 原因
[判明している範囲で]

■ 二次被害の有無
[判明している範囲で]

■ お願い事項
・パスワードの変更をお願いいたします
・他サービスで同じパスワードを使い回している場合は、そちらも変更をお願いいたします

ご不明点は info@kyurl.link までご連絡ください。
ご迷惑・ご心配をおかけし誠に申し訳ございません。
```

## 6. 体制(1人開発版)

チームでの役割分担ができないため、自分1人が以下を兼務する前提で動く。

| 役割 | やること |
|---|---|
| 検知・技術対応 | 第2節の緊急停止、原因調査 |
| 委員会報告 | 第3節の速報・確報フォーム提出 |
| 本人対応 | 第5節の通知メール送信、`info@kyurl.link`宛の問い合わせ対応 |
| 記録係 | タイムラインの記録(第7節) |

外部の専門家(弁護士等)への相談が必要と判断した場合は、判断に時間をかけすぎず早めに連絡する。
