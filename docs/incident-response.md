# 障害対応フロー

2026-09-20 制定 / 2026-09-21 改定 · @Someone
対象サービス: kyurl.link
関連文書: kyurl.link アーキテクチャドキュメント、漏えい等対応マニュアル

## 0. このマニュアルの位置づけ

kyurl.linkは1人開発・非商用ポートフォリオのため、一般的な「オンコール担当者間のエスカレーション」は成立しない。ここでは**「自分1人が気づいた時に何をするか」**と**「Cloudflare側起因の障害をどう切り分けてエスカレーションするか」**を中心にまとめる。24時間365日のSLAは掲げず、「気づき次第・ベストエフォート」を前提とする。

## 1. 重大度分類

| レベル | 内容 | 対応方針 |
|---|---|---|
| Sev1(最優先) | `/:shortCode`のリダイレクトが機能しない(コア機能停止) | 気づき次第、他の作業を止めて即対応 |
| Sev2 | QRコード生成・掲示物(ポスター)生成が失敗する | 当日〜翌営業日中を目安に対応 |
| Sev3 | ダッシュボード・認証(ログイン/サインアップ)のみ不調で、既存のリダイレクト・QR配信には影響しない | 数日以内を目安に対応 |
| Sev4 | 見た目の崩れ等、機能に影響しない軽微な不具合 | 手が空いた時に対応 |

判断基準: **「既存の短縮URL・QRコードを使っている来訪者(飲食店等の掲示物を見た一般ユーザー)に影響するか」**を最優先の判定軸とする。管理画面側の不調より、リダイレクト側の不調を常に優先する。

## 2. 検知手段

| 手段 | 用途 |
|---|---|
| **HetrixTools(無料プラン)** | リダイレクトエンドポイント(`/:shortCode`の代表的な1本)とヘルスチェック用エンドポイントを1分間隔・監視ロケーション4拠点で外形監視し、ダウン検知時にメール通知。「止まったことに気づく」役割。Cloudflareから完全に独立した外部SaaSのため、Cloudflare全体障害時にも独立して動作する |
| Workers Logs(`observability.enabled = true`) | エラー率・レイテンシの異常検知。「原因を調べる」役割で、HetrixToolsの通知後に確認する運用 |
| [Cloudflare Status](https://www.cloudflarestatus.com/) | Cloudflare全体(Workers/D1/R2/Browser Rendering等)の障害有無を切り分けるために確認 |
| 利用者からの問い合わせ(`info@kyurl.link`) | 自分で気づく前に利用者から報告が来るケースを想定し、問い合わせメールは即チェックする習慣を持つ |

**注意**: HetrixTools無料プランは、90日間ログインがないとアカウント(=モニター)が自動停止する。定期的なログインを運用ルールに含める。1人/1組織につき無料アカウントは1つまで(利用規約上の制約)。

## 3. 切り分け(自分の変更 vs Cloudflare側の障害)

1. 直近で自分がデプロイ・設定変更をしたか確認する → していれば自分の変更を疑う(第5節①へ)
2. Cloudflare Statusで該当プロダクト(Workers/D1/R2/Browser Rendering/Email)に障害が出ていないか確認する
3. 両方に該当しない場合は、外部要因(URLhaus等の外部API側の障害、DNS等)を疑う

## 4. エスカレーション先

| 原因 | エスカレーション先 |
|---|---|
| 自分のコード・設定変更が原因 | 自分自身が一次対応(第5節) |
| Cloudflare基盤側の障害 | Cloudflareサポート(Paidプランのサポートチケット)。復旧はCloudflare側の対応を待つほかないため、その間は利用者への告知(第6節)を優先する |
| 外部の脅威DB(URLhaus)等、悪意あるURL検知で参照している外部サービスの障害 | 第4節の既存方針(fail-open)で通常運用を継続。緊急のエスカレーション先は無し |

チームがいないため「エスカレーション先」といっても実質は「自分が動くか」「Cloudflareに問い合わせるか」の二択になる。

## 5. 対応手順

### ①自分の変更が原因の場合

1. 直近のデプロイ内容を確認する
2. 復旧を優先するか、原因調査を優先するか判断する(Sev1は復旧優先)
3. **ロールバック手段**
   - アプリケーションコード: Cloudflareダッシュボードから直前のデプロイへ巻き戻す
   - DBスキーマ・データ: D1 Time Travelで障害発生前の時点にロールバック
     ```bash
     # 現在のブックマーク(復元ポイント)を確認
     wrangler d1 time-travel info <DB_NAME>

     # 障害発生前の日時に復元(UNIXタイムスタンプ指定)
     wrangler d1 time-travel restore <DB_NAME> --timestamp=<UNIX_TIMESTAMP>
     ```
     - 保持期間: Workers Paidプランで**過去30日以内**の任意の時点まで復元可能(Freeプランは7日)
     - 復元操作の制限: 同一DBに対し**10分間に10回まで**
     - **本番DBに直接復元する前に、必ず別名のテストDB(例: `<DB_NAME>-restore-test`)に一度復元して中身を確認してから本番に反映する**(誤操作・二次被害の防止)
4. 復旧確認後、原因を記録する(第7節)

### ②Cloudflare基盤側が原因の場合

1. Cloudflare Statusで復旧状況を定期確認する
2. 復旧まで自分側でできる対応がないか検討する(例: Browser Renderingのみ障害なら掲示物生成だけ一時停止の告知をし、リダイレクト自体は継続提供)
3. 復旧後、影響範囲(何が・いつからいつまで止まっていたか)を記録する

## 6. 利用者への告知

専用のステータスページは当面用意しない。HetrixToolsはPublic Status Page機能を備えているが、対外アピールは控える方針を踏襲し、いったんPrivateで運用する。将来対外公開したくなった場合は、HetrixTools側の設定変更のみで追加実装コストなく対応できる。

- Sev1〜2相当で復旧に時間がかかる場合: トップページに簡易な告知文(例:「現在一部機能に不具合が発生しています」)を掲示する
- 問い合わせ(`info@kyurl.link`)が来た場合は個別に状況を回答する

## 7. 事後振り返り(簡易ポストモーテム)

大がかりな様式は使わず、以下の簡易メモをSev1・Sev2発生時のみ残す。

```
## 障害メモ: [タイトル]
発生日時: 
検知方法: 
影響範囲: [リダイレクト/QR生成/ダッシュボード等、どの機能が、いつからいつまで]
原因: 
対応内容: 
再発防止策: [あれば]
```

Sev3・Sev4は簡易メモも省略してよい。

## 8. 引き続きの検討事項

- ~~自動監視・アラートをどこまで実装するか~~ → **HetrixTools無料プランで外形監視+通知を導入する方針で確定**(第2節)。無料プランの利用規約に「監視サービス自体の商用利用禁止」の明記はなく、UptimeRobotで懸念していたB2B化時の制限は実質解消(ただしB2B化のタイミングで念のため再確認する)。無料プランは90日間ログインがないとモニターが停止するため、定期ログインを運用ルールに含める
- ~~専用ステータスページを用意するか~~ → **当面は用意しない方針で確定**(第6節)。HetrixToolsのPublic Status Page機能は利用可能な状態にあるため、将来必要になれば設定変更のみで対応できる
- ~~D1 Time Travelの具体的な運用手順~~ → `wrangler d1 time-travel info/restore`コマンドと、テストDBへの事前復元手順を明記して確定(第5節①)
